## The diagnostic chain (the part worth remembering)

> The single most important lesson of this session: **fixing one
> silent-skip class doesn't fix the next level up unless the fix
> itself is enforced mechanically.** E1.a was a structural fix for
> agent envelope shape, but E1.a was *itself* written as an INSTRUCTION
> in the prompt. The instruction-vs-gate distinction has to be applied
> recursively — every layer of the contract that matters has to be
> enforced by the parser, not asserted by the prompt.

### Symptoms

After E1.1 stamped the CRITICAL OUTPUT CONTRACT onto security-reviewer
+ tdd-guide + e2e-runner (and `pe gate parse` round-tripped each
agent's exemplar B JSON cleanly), the operator required a fresh
runtime invocation before declaring E1.1 held — exactly because E1.c
had proven that "parser accepts envelope" ≠ "agent runs on the right
model."

Runtime check on `security-reviewer` against a planted-vuln Flask
fixture (`/tmp/e1_1_runtime_fixture/vulnerable_endpoint.py`) returned
**partial pass:**

| Criterion | Result |
|---|---|
| `model_used: claude-sonnet-*` | ✓ `claude-sonnet-4-6` — tier routing held |
| CRITICAL OUTPUT CONTRACT followed | ⚠ envelope shape correct, but no "Envelope key values" cross-check block |
| Envelope round-trips through `pe gate parse` | ✓ exit 1 (FAIL/worker_quality) |

Two of three held. One didn't.

### Wrong diagnosis attempted (rejected up-front)

> "Soft-pass: the load-bearing gate (schema validation) held; the
> cross-check is a self-help rail meant to catch schema failures, and
> schema already passed. Note it, move on."

The operator rejected this in writing — and correctly: a quality step
written as an instruction has the same failure-mode risk as E1.c,
just smaller. Letting it slide unwinds E1.a's principle (stop trusting
the agent to "do the right thing"). Phase 3 routes on these envelopes
and needs to know the agent did its **whole** process, not just
shipped valid JSON.

### Real root cause

E1.a (PR #1) replaced "trust the prompt" with "validate via `pe gate
parse`" for the envelope's *shape*. But the cross-check section
(`# Pre-emission cross-check — print the values, don't just tick
boxes`) stayed entirely prose:

> "In your reply, **before** the final fenced envelope, print a short
> 'Envelope key values' section that literally shows each required
> field's value."

This is the exact pattern E1.a's preamble warns against — an
"asserted-by-prose claim" with no tool-level enforcement. The agent
skipped it for the same reason E1.a's earlier fixes were needed:
mid-context emphasis shifts. The CRITICAL OUTPUT CONTRACT preamble
says "**this section is law**" but didn't carve out which subsections
were tool-enforced vs. trust-based. The cross-check fell on the
trust-based side and got skipped.

### The structural fix (E1.d, PR #6)

One parser. One exit-code path. **Cross-check presence and value-match
are now schema-error-class failures (exit 4)**, identical handling to
"banned field name" or "non-kebab-case rule."

`scripts/pe_gate.py` default mode now requires the input to contain
BOTH the fenced envelope AND an `Envelope key values` block whose
6 required envelope fields (`schema_version`, `gate_name`, `verdict`,
`failure_class`, `model_used`, `timestamp`) literally equal the
envelope. A new `--bare` flag preserves legacy raw-JSON tolerance for
fixtures only — agents must not reach it from their self-validation
step.

The contract template (`agents/code-reviewer.md`) was updated so the
agent's self-validation step writes a TRANSCRIPT
(`/tmp/gate-envelope-draft.md`) containing both blocks, not raw JSON.
The agent literally cannot pass its own self-validation while
omitting the cross-check.

The 3 ported agents were reverted to `feat/e1-gate-envelope` baseline
and re-ported from the updated template via the same
`/tmp/e1_1_rollout.py` script, so all four gate agents track the
canonical template byte-for-byte (modulo per-agent customization).

|---|---|---|---|---|

| tdd-guide | claude-sonnet-4-6 | ✓ | ✓ | 1 |

Verified twice per agent: once by the agent's own self-validation

**E1.1 is held under the E1.d-hardened contract.**

### Re-usable lesson (same class as the stale-shadow chain)

The 2026-06-24 session's lesson was "a bug that looks like one class
of problem can be a completely different class of problem in
disguise" — a prompt-engineering symptom (`model:` not honored) had a
filesystem root cause (stale-shadow propagation).

The 2026-06-25 session's lesson is the inverse: **the same root-cause
class can recur at higher levels of abstraction unless the fix is
applied to its own metarule.** E1.a fixed "trust prompts to constrain
envelope shape" by adding tool-level validation. But E1.a was itself a
prompt-level instruction about which validation to run. The "prompt
asserts X" pattern recurred at the next level up. E1.d fixes it by
folding the metarule into the same parser path:

> If quality step Q is enforced via tool exit-code path P, any
> subsequent step Q' that exists to validate Q must also be enforced
> via P — not asserted in prose adjacent to P. Otherwise Q' is a new
> trust-based assertion in the same bucket the original Q was rescued
> from.

Operationally, for any future contract addition:

- If "the agent must do X" is added to the prompt
- And X is a verifiable presence/match/format property
- Then X must be enforced by extending `pe gate parse`, not by adding
  prose to the contract section.

This is the principle Phase 3's escalation router will silently
depend on. Without it, "the agent emitted a passing envelope" doesn't
imply "the agent did the whole gate process," and routing decisions
made on the former while assuming the latter are quietly wrong.

## What's now structurally true

1. **Tiered routing held a second time.** First proof was E1.c
   (`code-reviewer` switched from haiku to sonnet after `pe install`
   created the project-local symlink). Second proof was this session
   — all 3 freshly-ported agents reported `claude-sonnet-4-6` on
   first invocation. The propagation-gap fix (PR #4) holds.
2. **Cross-check is mechanically enforced.** The agent cannot emit a
   passing self-validation without including the cross-check block
   AND making its values match the envelope. Phase 3 router can
   trust "exit 0/1/2/3" to mean "the agent did the whole process,"
   not just "the JSON parses."
3. **Single parser, single exit-code path.** No second-level gate
   logic. Future contract additions extend `pe gate parse` rather
   than adding parallel checks — closes the recursive
   prompt-asserts-X gap before it opens.
4. **The substitution script is reusable.** `/tmp/e1_1_rollout.py`
   reads the canonical contract from `code-reviewer.md`, applies
   per-agent customizations, and appends to target agent files.
   Re-applied successfully after the E1.d template update — proves
   the "revert + reapply" loop is the right tool for keeping all
   gate agents byte-identical to the canonical template.
